# DAX Extraction Reference

Domain knowledge for extracting data from Power BI semantic models via MCP tool calls, converting DAX results to CSV, and handling fiscal calendar conventions.

---

## 1. MCP Connection & Exploration Sequence

Execute these tool calls in order. Each step depends on the prior step succeeding.

### Step 1: Connect to the Semantic Model

```
Tool:  mcp__powerbi-modeling-mcp__connection_operations
Parameters:
  action:            ConnectFabric
  workspaceName:     "FT Data Analytics PRD"
  semanticModelName: "FT Customer Analytics"
```

**Expected result:** Connection confirmation with model metadata summary.

**If connection fails:**
- Verify the workspace name matches exactly (case-sensitive).
- Verify the semantic model is published and not paused.
- Verify the MCP server is running (`powerbi-modeling-mcp` must be configured in the environment).

### Step 2: Explore the Model

```
Tool:  mcp__powerbi-modeling-mcp__model_operations
Parameters:
  action: GetModel
```

**Expected result:** Model-level metadata including name, culture, default mode, and compatibility level. Use this to confirm you are connected to the correct model.

### Step 3: List All Tables

```
Tool:  mcp__powerbi-modeling-mcp__table_operations
Parameters:
  action: ListTables
```

**Expected result:** Array of table names with their types (regular, calculated, date). Record these for column exploration and DAX query construction.

**Key table types:**
- **Regular tables** -- sourced from DirectLake or Import; contain the actual data.
- **Calculated tables** -- generated by DAX expressions; typically bridging or utility tables.
- **Date tables** -- marked as the model's date table; contain fiscal calendar columns.

### Step 4: List Columns for a Specific Table

```
Tool:  mcp__powerbi-modeling-mcp__column_operations
Parameters:
  action:    ListColumns
  tableName: "DimCustomer"
```

**Expected result:** Array of column definitions including name, data type, source column, and whether the column is hidden. Repeat this call for each table relevant to the analysis.

**Tip:** Start with dimension tables to understand available grouping columns, then check fact tables for the measures and additive columns.

### Step 5: Execute a DAX Query

```
Tool:  mcp__powerbi-modeling-mcp__dax_query_operations
Parameters:
  action: ExecuteQuery
  query:  "EVALUATE SUMMARIZECOLUMNS('DimDate'[Fiscal_Month], \"PAU\", [PAU])"
```

**Expected result:** JSON object with `columns` (array of column metadata) and `rows` (array of row arrays). Column metadata includes `name` and `type`.

**Timeout:** Large queries may take 30-60 seconds. If the query times out, add filters to reduce the result set (see Section 7, pitfall #6).

## 2. DAX Query Patterns

All patterns use `EVALUATE` + `SUMMARIZECOLUMNS`, which is the standard shape for tabular result extraction. Each pattern is complete and runnable.

### Pattern 1: Time Series Extraction

Monthly metrics with fiscal year ordering. Use when you need trend data over time.

```dax
EVALUATE
SUMMARIZECOLUMNS(
    'DimDate'[Fiscal_Year],
    'DimDate'[Fiscal_Month],
    'DimDate'[Month_Sort],
    "PAU", [PAU],
    "Record_Count", COUNTROWS('FactUsage')
)
ORDER BY
    'DimDate'[Fiscal_Year] ASC,
    'DimDate'[Month_Sort] ASC
```

**When to use:** Trend analysis, growth curves, month-over-month comparisons.
**Key columns:** Always include `Month_Sort` alongside `Fiscal_Month` for correct ordering (see Section 5).

### Pattern 2: Dimensional Aggregation

Metrics grouped by a single categorical dimension. Use when you need segment-level comparisons.

```dax
EVALUATE
SUMMARIZECOLUMNS(
    'DimWorkload'[Workload_Family],
    "Win_Rate", [Win Rate],
    "Customer_Count", [Customer Count],
    "PAU", [PAU]
)
ORDER BY
    [Win_Rate] DESC
```

**When to use:** Category rankings, Pareto analysis, segment comparisons.
**Key consideration:** Include a count measure (e.g., `Customer_Count`) alongside rates so you can assess statistical significance downstream.

### Pattern 3: Cross-Dimensional Breakdown

Metrics broken down by two or more dimensions simultaneously. Use when you need to analyze interactions between categories.

```dax
EVALUATE
SUMMARIZECOLUMNS(
    'DimWorkload'[Workload_Family],
    'DimCustomer'[EOU],
    'DimDate'[Fiscal_Year],
    "Win_Rate", [Win Rate],
    "Customer_Count", [Customer Count],
    "PAU_Total", [PAU]
)
ORDER BY
    'DimWorkload'[Workload_Family] ASC,
    'DimCustomer'[EOU] ASC
```

**When to use:** Heatmap analysis, interaction effects, multi-factor breakdowns.
**Key consideration:** Each additional dimension multiplies the row count. Two dimensions with 10 values each produce up to 100 rows; three dimensions can produce thousands. Always estimate the expected row count before executing.

### Pattern 4: Flat Snapshot (KPI Summary)

Single-row summary of headline metrics. Use for dashboard KPI cards and executive summaries.

```dax
EVALUATE
ROW(
    "Total_Customers", [Customer Count],
    "Total_PAU", [PAU],
    "Overall_Win_Rate", [Win Rate],
    "CFY_Active_Count", CALCULATE([Customer Count], 'DimDate'[Is_CFY] = TRUE())
)
```

**When to use:** Dashboard headline numbers, single-point-in-time summaries.
**Key consideration:** `ROW()` always returns exactly one row. All measures evaluate in the default filter context of the model (typically all data) unless wrapped in `CALCULATE` with explicit filters.

### Pattern 5: Filtered Extraction with TREATAS

Metrics for a specific subset of the data, using virtual relationships or filter injection.

```dax
EVALUATE
SUMMARIZECOLUMNS(
    'DimCustomer'[Customer_Name],
    'DimCustomer'[TPID],
    'DimWorkload'[Workload_Family],
    TREATAS({"FY26"}, 'DimDate'[Fiscal_Year]),
    "PAU", [PAU],
    "Win_Rate", [Win Rate]
)
ORDER BY
    [PAU] DESC
```

**When to use:** When you need to filter to a specific fiscal year, segment, or cohort without modifying the model.
**Key consideration:** `TREATAS` creates a virtual relationship filter. The filter values must match the column's data type exactly (string for string, integer for integer).

### Pattern 6: TOPN Extraction

Top N entities by a metric. Use when you need ranked lists or outlier identification.

```dax
EVALUATE
TOPN(
    20,
    SUMMARIZECOLUMNS(
        'DimCustomer'[Customer_Name],
        'DimCustomer'[TPID],
        "PAU", [PAU]
    ),
    [PAU], DESC
)
ORDER BY
    [PAU] DESC
```

**When to use:** "Top 20 customers by PAU," outlier detection, ranked segment analysis.
**Key consideration:** `TOPN` evaluates the full result set internally before trimming. Performance is similar to an unfiltered query with a post-filter.

## 3. Column Type Mapping

When converting DAX query results to CSV, map data types as follows:

| DAX Type | Python Type | CSV Format | Notes |
|----------|-------------|------------|-------|
| `DateTime` | `str` | `YYYY-MM-DD` (ISO 8601) | Convert with `pd.to_datetime(col).dt.strftime('%Y-%m-%d')`. Drop time component unless the analysis requires sub-day granularity. |
| `Decimal` | `float` | 4 decimal places | Use `round(col, 4)`. Rates and proportions should retain 4 decimals for downstream Wilson CI calculations. |
| `Integer` | `int` | No decimals | Use `astype(int)` after handling NaN (see BLANK() note below). |
| `String` | `str` | As-is | Replace DAX `BLANK()` with empty string `""`, not `NaN`. |
| `Boolean` | `int` | `1` / `0` | Convert `True`/`False` to `1`/`0` with `astype(int)`. |
| `Double` | `float` | 4 decimal places | Same treatment as Decimal. |

**BLANK() handling:** DAX returns `BLANK()` for missing values. In the JSON result, these appear as `null`. Pandas converts `null` to `NaN`. For string columns, replace `NaN` with `""`. For numeric columns, decide based on context: `NaN` is appropriate for missing metrics, but `0` may be appropriate for missing counts. Document the choice in Data Definitions.

## 4. CSV Conversion Pattern

Standard Python pattern for converting DAX query results to a pandas DataFrame and writing to CSV.

```python
import pandas as pd

def dax_result_to_dataframe(result: dict) -> pd.DataFrame:
    """
    Convert DAX query result dict to a pandas DataFrame.

    Args:
        result: Dict with "columns" (list of {"name": str, "type": str})
                and "rows" (list of lists).

    Returns:
        DataFrame with properly named columns.
    """
    columns = [col["name"] for col in result["columns"]]
    df = pd.DataFrame(result["rows"], columns=columns)
    return df


def clean_and_export(df: pd.DataFrame, output_path: str) -> None:
    """
    Apply standard type cleaning and write CSV.

    - Dates to ISO 8601 strings
    - Decimals rounded to 4 places
    - BLANK()/NaN in string columns replaced with empty string
    - UTF-8 BOM encoding for Excel compatibility
    """
    for col in df.columns:
        if df[col].dtype == "object":
            # String columns: replace NaN with empty string
            df[col] = df[col].fillna("")
        elif pd.api.types.is_float_dtype(df[col]):
            # Float columns: round to 4 decimal places
            df[col] = df[col].round(4)

    df.to_csv(output_path, index=False, encoding="utf-8-sig")
    print(f"Exported {len(df)} rows x {len(df.columns)} columns to {output_path}")
```

**Usage:**

```python
# After executing DAX query via MCP tool
df = dax_result_to_dataframe(query_result)
clean_and_export(df, "data/win-rates-by-workload.csv")
```

**Why `utf-8-sig`:** The BOM (byte order mark) ensures Excel opens the file correctly without the "garbled characters" problem that occurs with plain `utf-8` encoding on Windows.

## 5. Fiscal Year Month_Sort Pattern

Microsoft's fiscal year runs July through June. When data contains fiscal month columns, add a `Month_Sort` column for correct chronological ordering.

### Sort Mapping

| Calendar Month | Fiscal Month | Month_Sort |
|----------------|--------------|------------|
| July           | July         | 1          |
| August         | August       | 2          |
| September      | September    | 3          |
| October        | October      | 4          |
| November       | November     | 5          |
| December       | December     | 6          |
| January        | January      | 7          |
| February       | February     | 8          |
| March          | March        | 9          |
| April          | April        | 10         |
| May            | May          | 11         |
| June           | June         | 12         |

### Implementation

**Option A: Include Month_Sort in the DAX query** (preferred)

If the semantic model has a `Month_Sort` or `Fiscal_Month_Number` column on the date table, include it directly in the DAX query (see Pattern 1 in Section 2). This is the most reliable approach because it uses the model's own fiscal calendar definition.

**Option B: Add Month_Sort in Python** (fallback)

If the model does not expose a sort column, add it after extraction:

```python
FISCAL_MONTH_ORDER = {
    "July": 1, "August": 2, "September": 3,
    "October": 4, "November": 5, "December": 6,
    "January": 7, "February": 8, "March": 9,
    "April": 10, "May": 11, "June": 12
}

df["Month_Sort"] = df["Fiscal_Month"].map(FISCAL_MONTH_ORDER)
df = df.sort_values(["Fiscal_Year", "Month_Sort"])
```

**Why this matters:** Without `Month_Sort`, tools that sort alphabetically will order months as April, August, December, ... -- completely wrong for trend analysis. Every CSV that contains fiscal month data must include this column.

## 6. Analyst Prompting Guidance

When an analyst describes the data they need, ask these questions to ensure the extraction is complete. The goal is to get the full picture before writing any DAX, because adding a forgotten dimension later requires re-running the entire pipeline.

### Question 1: What dimensions do you need?

"What groupings or categories do you want to break the data down by?"

**Examples:**
- Workload family (Teams, Exchange, SharePoint)
- Region or EOU (Americas, EMEA, APJ)
- Customer segment (Enterprise, SMB)
- Time period (fiscal month, fiscal quarter, fiscal year)
- Engagement type (PEC status, FTA assignment)

**Follow-up:** "Is there any dimension you might want to filter or pivot by later, even if it is not your primary focus? It is much cheaper to include it now than to re-extract."

### Question 2: What measures do you need?

"What numbers or rates do you want to analyze?"

**Examples:**
- PAU (Paid Available Units)
- Win Rate
- Customer Count
- DPU (Deep Protected Users)
- MAU (Monthly Active Users)

**Follow-up:** "Do you need both a rate and the underlying count? Counts are needed for statistical significance testing downstream."

### Question 3: What filters apply?

"What time period, segments, or conditions should limit the data?"

**Examples:**
- Current fiscal year only (CFY)
- CFY prioritized customers only
- Specific workload families
- Customers above a PAU threshold

**Follow-up:** "Should the filter be applied in the DAX query (hard filter, reduces row count) or kept as a column so you can compare filtered vs. unfiltered groups?"

### Question 4: What is the grain?

"What does one row in the output represent?"

**Examples:**
- One row per customer per workload per month
- One row per workload family per fiscal year
- One row per EOU (total aggregation)

**Follow-up:** "If you are unsure, start with the finest grain that includes all your dimensions. You can always aggregate up in analysis, but you cannot disaggregate after extraction."

### Question 5: Will you need to compare groups?

"Are you comparing two or more groups (e.g., PEC vs. non-PEC, before vs. after)?"

If yes, ensure the grouping variable is included as a dimension column, not as a filter. The analysis phase needs both groups in the same dataset to compute lift, chi-square, and NNT.

## 7. Common Pitfalls

### Pitfall 1: Duplicate Rows from Many-to-Many Relationships

**Symptom:** Row count is much higher than expected. The same customer appears multiple times for the same month.

**Cause:** The semantic model has a many-to-many relationship (e.g., a customer belongs to multiple segments). `SUMMARIZECOLUMNS` produces one row per unique combination, so a customer in 3 segments appears in 3 rows.

**Fix:** Either (a) filter to one side of the many-to-many relationship using `TREATAS` or `CALCULATETABLE`, or (b) accept the fan-out and document the grain as "one row per customer per segment per month" in Data Definitions. Never silently deduplicate -- the duplicates carry real meaning.

### Pitfall 2: Missing Filters Causing Full Table Scan

**Symptom:** Query returns millions of rows or times out. The result includes historical data from many fiscal years.

**Cause:** No time filter was applied. The model contains years of historical data, and `SUMMARIZECOLUMNS` returns all of it by default.

**Fix:** Always include a time filter for large models. Use `TREATAS` for fiscal year filtering (see Pattern 5) or include a fiscal year dimension column and filter in Python post-extraction. Prefer DAX-side filtering for performance.

### Pitfall 3: BLANK() Values Becoming NaN in Pandas

**Symptom:** String columns contain `NaN` instead of empty strings. Downstream groupby operations create a separate `NaN` group. Charts show "nan" as a label.

**Cause:** DAX `BLANK()` maps to JSON `null`, which pandas imports as `NaN` regardless of column type.

**Fix:** Apply the type-aware cleaning in Section 4. For string columns, use `fillna("")`. For numeric columns, decide whether `NaN` or `0` is semantically correct and document the choice.

### Pitfall 4: Fiscal Calendar vs. Calendar Year Mismatch

**Symptom:** "FY26 January" data does not match what the analyst expects. Trend charts show months in the wrong position.

**Cause:** The analyst is thinking in calendar year (January 2026) but the model stores fiscal year context (FY26 January = January 2026, which is fiscal month 7 of FY26). Alternatively, the `Month_Sort` column is missing and months are sorted alphabetically.

**Fix:** Always confirm fiscal year context with the analyst: "When you say January 2026, you mean FY26 month 7, correct?" Include `Month_Sort` in every time-series extraction (see Section 5). Never assume calendar year ordering.

### Pitfall 5: Measure Context Not Matching Expected Grain

**Symptom:** A rate measure (e.g., Win Rate) returns the same value for every row, or returns unexpected values when grouped by certain dimensions.

**Cause:** The measure was authored to evaluate at a specific grain (e.g., customer level), but `SUMMARIZECOLUMNS` is requesting it at a different grain (e.g., workload level). DAX measures evaluate in the filter context created by the grouping columns, which may not match the measure's internal logic.

**Fix:** Check the measure definition using `mcp__powerbi-modeling-mcp__measure_operations` with action `GetMeasure`. Understand whether the measure uses `CALCULATE`, `ALL`, `ALLEXCEPT`, or other context-modifying functions. If the measure is not designed for the requested grain, you may need to write a wrapper measure or extract at the measure's native grain and aggregate in Python.

### Pitfall 6: Large Result Sets Timing Out

**Symptom:** The MCP tool call hangs or returns an error after 60+ seconds. No data is returned.

**Cause:** The DAX query produces too many rows. Cross-dimensional queries with several high-cardinality columns (e.g., customer name x workload x month) can produce hundreds of thousands of rows.

**Fix:** Apply these strategies in order:
1. **Filter first:** Add `TREATAS` filters to limit to the relevant fiscal year or segment.
2. **Reduce dimensions:** Remove the highest-cardinality dimension (often customer name) and use TPID or a rollup instead.
3. **Paginate:** Split the query into multiple calls by dimension value (e.g., one query per EOU).
4. **Estimate before executing:** Calculate expected rows = product of unique values across all dimension columns. If the estimate exceeds 50,000 rows, restructure the query.

### Pitfall 7: Column Name Collisions in SUMMARIZECOLUMNS

**Symptom:** The query fails with an error about duplicate column names.

**Cause:** Two tables have columns with the same name (e.g., both `DimCustomer` and `DimWorkload` have a `Name` column). `SUMMARIZECOLUMNS` flattens the result, creating a collision.

**Fix:** Use the full qualified column name in the DAX query: `'DimCustomer'[Name]` and `'DimWorkload'[Name]`. In the result, these will appear as `DimCustomer[Name]` and `DimWorkload[Name]`. Rename them to clearer names in Python post-extraction:

```python
df = df.rename(columns={
    "DimCustomer[Name]": "Customer_Name",
    "DimWorkload[Name]": "Workload_Name"
})
```
